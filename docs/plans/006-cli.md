# CLI for lexicon authors

## Capabilities covered

- C14 — A lexicon author can run `lexiqr validate my-lexicon.json` and get the same precise, human-readable errors the library raises at load time.
- C15 — A lexicon author can run `lexiqr try my-lexicon.json --locale de-DE "wo ist flooff"` and see the full match report in the terminal, without writing Python.

## Problem

Lexicon authors (tenant admins, CS engineers, localization specialists) maintain lexicons but never write Python. The skeleton's `lexiqr try` is happy-path only; authors need a complete no-Python loop: validate a file, try prompts against it, read the results.

## Solution

Complete the argparse CLI per ADR 0002's hard boundary — the CLI only calls core's public API. `lexiqr validate` loads the file and renders core's structured `ValidationError`s (entity/locale/field) human-readably; error parity with the library is a test, not a promise. `lexiqr try` renders the full match report: matches with spans (visually marked in the prompt), score tiers, corrections, and matched locales. Clean exit codes for scripting (0 valid/matched, non-zero otherwise).

## Scope

- `lexiqr validate <file>`: full error rendering, parity test against library load errors.
- `lexiqr try <file> --locale <loc> "<prompt>"`: full report rendering incl. correction and matched-locale fields; useful output for zero matches.
- Exit codes, `--help` texts, and a boundary test that `cli.py` imports only the public API.

## Out of scope

- Any logic beyond rendering (validation and matching live in core); interactive/REPL mode; output formats beyond human-readable text (a `--json` flag can be a post-1.0 nicety).

## Dependencies

002 — foundations (validation errors). Full report rendering needs 004 and 005 fields; schedule after both.
